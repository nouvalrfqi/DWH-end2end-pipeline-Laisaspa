# 1. Executive Summary

This project builds an end-to-end modern data platform for a Spa & Wellness business using operational data generated by a POS/web application.

The platform will transform operational OLTP data into reliable analytical datasets and business dashboards through the following flow:

```text
Supabase PostgreSQL (OLTP)
        |
        v
Python Generic Extraction Framework
        |
        v
AWS S3 RAW Data Lake
        |
        v
Snowflake STAGING
        |
        v
Snowflake WAREHOUSE
        |
        v
dbt Transformation
        |
        v
Snowflake MART
        |
        v
Power BI
```

Apache Airflow will orchestrate and schedule the complete pipeline after the individual pipeline components have been validated.

The project is intentionally developed incrementally. Initial ingestion will use CSV in the raw layer. Once the pipeline is stable, the raw format will be upgraded to Parquet.

# 3. Architecture Principles

The project follows these principles:

## 3.1 Separation of Concerns

Each technology has a clear responsibility.

| Component | Responsibility |
|---|---|
| Supabase PostgreSQL | Operational OLTP |
| Python | Extraction and ingestion framework |
| AWS S3 | Raw Data Lake |
| Snowflake STAGING | Source standardization and cleansing |
| Snowflake WAREHOUSE | Integrated dimensional model |
| dbt | Transformation, modeling, testing, documentation |
| Snowflake MART | Business-oriented analytical datasets |
| Airflow | Workflow orchestration and scheduling |
| Docker | Reproducible runtime environment |
| GitHub | Version control |
| GitHub Actions | CI/CD |
| Power BI | Business intelligence and visualization |

## 3.2 Raw Data Preservation

The raw layer should preserve source data as faithfully as practical.

Raw ingestion should not apply business logic.

## 3.3 Idempotency

Running the same pipeline batch repeatedly should not create unintended duplicate analytical data.

## 3.4 Reusability

Extraction logic should be generic and configuration-driven rather than duplicated per table.

## 3.5 Least Privilege

Cloud credentials and service accounts receive only the permissions required for their tasks.

## 3.6 Incremental Evolution

The project starts with a simple, testable batch pipeline and progressively introduces:

- Parquet
- incremental loading
- Airflow
- dbt
- Docker
- testing
- CI/CD
- monitoring

# 7. Data Lake Design

## 7.1 AWS S3 Role

AWS S3 is the project's Data Lake storage layer.

It is not the primary analytical warehouse.

## 7.2 Bucket

Target bucket:

```text
spa-data-platform-dev
```

The exact bucket name may vary if the chosen name is unavailable globally.

## 7.3 Security

The bucket must:

- block public access;
- use server-side encryption;
- use an IAM principal with least-privilege permissions;
- never expose credentials in source code;
- never commit `.env` or secrets to Git.

## 7.4 S3 Structure

Initial structure:

```text
spa-data-platform-dev/
|
+-- raw/
|
+-- logs/
|
+-- archive/       # optional
```

The primary data lake responsibility is RAW data.

STAGING, WAREHOUSE, and MART are not required to be represented as S3 folders because those analytical layers will reside in Snowflake.

# 8. Raw Data Strategy

## 8.1 Initial Format

CSV.

Reason:

- easy to inspect;
- easy to debug;
- simple to implement;
- suitable for the first ingestion milestone.

## 8.2 Future Format

Parquet.

After the pipeline is stable, raw files should be migrated to Parquet to demonstrate:

- columnar storage;
- better analytical scan efficiency;
- compression;
- schema-aware storage;
- data lake best practices.

## 8.3 Partitioning

The raw path should use date-based partitioning.

Example:

```text
raw/
  transactions/
    year=2026/
      month=08/
        day=07/
          transactions_20260807_220000.csv
```

The timestamp should represent the ingestion/batch time, not necessarily the business event time.

# 9. Extraction Framework

## 9.1 Objective

Build one reusable Python extraction framework capable of extracting multiple PostgreSQL tables based on configuration.

Do not create one independent extractor per source table.

Bad pattern:

```text
extract_treatments.py
extract_members.py
extract_transactions.py
extract_reviews.py
```

Preferred pattern:

```text
generic_extractor.py
+
configuration
```

## 9.2 Configuration-Driven Design

Example conceptual configuration:

```yaml
tables:
  - treatments
  - spa_products
  - booking_groups
  - booking_logs
  - transactions
  - completed_items
  - members
  - gift_cards
  - reviews
  - spa_consultations
```

The framework should:

1. load configuration;
2. connect to PostgreSQL;
3. iterate through configured tables;
4. extract data;
5. perform extraction-level validation;
6. serialize the result;
7. upload to S3;
8. record metadata;
9. record success/failure;
10. continue or fail according to defined error policy.

# 10. Extraction Modes

## Phase 1

Full load.

Every configured table is extracted completely.

## Phase 2

Incremental load.

Where source tables contain appropriate timestamp columns, use a watermark strategy based on fields such as:

```text
created_at
updated_at
```

The actual incremental key must be selected only after inspecting each table.

# 11. Data Validation Strategy

Data validation is broader than checking row counts.

## 11.1 File Validation

Check:

- file exists;
- file is not empty;
- file can be read;
- expected format is produced.

## 11.2 Schema Validation

Check:

- expected columns exist;
- unexpected structural changes are detected;
- data types are reasonable;
- column count is consistent.

## 11.3 Row Count Validation

Compare source and extracted counts for full-load batches.

Example:

```text
PostgreSQL: 5,382 rows
S3 extract: 5,382 rows
Status: PASS
```

## 11.4 Data Quality Validation

Where applicable:

- null checks;
- primary-key uniqueness;
- duplicate detection;
- accepted-value checks;
- numeric range checks;
- date validity.

## 11.5 Business Rule Validation

Examples:

```text
price >= 0
rating between 1 and 5
transaction identifier not null
```

Business rules must be based on confirmed source/business requirements.

- dependency management;
- reusable models;
- testing;
- documentation;
- lineage;
- deployment-oriented SQL workflows.

Conceptual flow:

```text

   |
   v

   |
   +--> MART models
```

```text

        |
        v
```

# 16. Incremental Loading Strategy

After the full-load pipeline works, implement incremental loading.

Conceptual approach:

```text
Previous successful watermark
          |
          v
PostgreSQL
          |
          | WHERE updated_at > watermark
          v
New/changed records
          |
          v
S3
          |
          v
Snowflake
```

The design must avoid duplicate analytical records.

Where necessary, Snowflake MERGE logic should be used.

---

# 17. Idempotency

Every major task should be designed so that retrying a failed task does not corrupt downstream data.

Examples:

- deterministic batch IDs;
- controlled S3 object keys;
- staging replacement or merge strategy;
- warehouse MERGE where appropriate;
- dbt incremental models where appropriate.

# 26. AI IDE Collaboration Rules

The AI coding assistant must follow these rules.

## Rule 1 — Do Not Change Architecture Without Approval

Do not replace:

```text
S3
Snowflake
dbt
Airflow
```

with alternative technologies unless explicitly requested.

## Rule 2 — Inspect Existing Code First

Before creating or modifying code:

- inspect repository structure;
- inspect configuration;
- inspect related modules;
- preserve existing conventions.

## Rule 3 — Do Not Invent Source Columns

Never assume a PostgreSQL column exists.

Inspect the actual schema first.

## Rule 4 — Do Not Hardcode Secrets

Never write credentials directly into source code.

## Rule 5 — Prefer Generic Components

Avoid table-specific code when the same behavior can be generalized.

## Rule 6 — Explain Major Technical Decisions

For significant changes, document:

- problem;
- decision;
- reason;
- consequence.

## Rule 7 — Test Before Expanding Scope

A working component must be validated before building downstream components.

## Rule 8 — Preserve Data Lineage

Every analytical dataset should be traceable:

```text
Power BI
   ↓

   ↓

   ↓

   ↓

   ↓
```
